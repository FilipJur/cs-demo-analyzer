# 01 — CS2/CSGO Demo Parsing & Programmatic Tooling Layer

**Slice owner:** `EcosystemSurvey.ParsersLibs` · **Written:** 2026-10-15 · **Recency window:** 2024 → 2026-10-15
**Goal:** determine the best foundation for a local-first, API-powered CS2 demo-analysis / personal-coaching system, and establish exactly what visibility ("fog of war"), input, and per-tick data the parsing layer can actually deliver.

**Method / evidence rules.** Every version and date below was read from a primary machine-readable source, not from prose: PyPI JSON API, npm registry JSON, crates.io API, GitHub REST API, GitHub `.atom` commit/release feeds, raw source files (`raw.githubusercontent.com`), and `curl`-fetched raw files from clones of `pnxenopoulos/awpy`, `LaihoE/demoparser`, `markus-wa/demoinfocs-golang` (shallow, main branches, fetched 2026-10-15). Claims about API behaviour come from *source code or test code*, not README marketing. Anything not directly observed is tagged `[INFERENCE]`.

Claim tags used: **Demonstrated** (read in source/test/released artifact) · **Experimental** (shipped but explicitly unvalidated by its own authors) · **Research-supported** (validated against an external ground truth) · **Plausible-untested** · **Infeasible**.

## 1. awpy 3.x (pnxenopoulos/awpy) — the current flagship Python CS2 parser

- **What it does.** Python-facing CS2 demo parser + analysis library: typed, cached **Polars DataFrames** for combat/grenade/player datasets, a Rust core, map-geometry line-of-sight (`VisibilityChecker`), nav-mesh pathfinding (`NavMesh`), map-control estimation, plotting, a CLI, and a Rust library API for the same core.
- **CS2 demo support (verified how).** **Demonstrated.** `awpy` is CS2-only by design: its own FAQ states it reads "Counter-Strike 2 demos in the PBDEMS2 format… It does not read CS:GO demos" (`crates/awpy-python/docs/faq.md`, main @ 2026-10-15). The Rust workspace contains the CS2 protobufs (`crates/awpy-proto`, generated with `prost`, tracked to CS2 build `2000924`, source revision `11076591`) and per-build field decoders / name tables, with CI that diffs bundled protos against upstream (`docs/changelog.md`, 3.0.0 entry).
- **Maintenance status.** **Very active.** PyPI latest `awpy 3.0.0`, uploaded **2026-10-14T04:33Z** (`https://pypi.org/pypi/awpy/json`); GitHub release `awpy-python-v3.0.0` published 2026-10-14T04:34Z; repo `pushed_at` **2026-10-15T01:05Z**, 618★, 85 forks, 5 open issues. Commits on `main` dated 2026-10-15: "multipart demos (#527)", "fix adr (#528)" — i.e. **3.1.0 is on `main` but not yet on PyPI** (Cargo workspace version is `3.1.0`; PyPI still shows 3.0.0). Prior 2.x line: `2.0.0` 2025-03-03, `2.0.1` 2025-03-06, `2.0.2` 2025-03-10 — so **the "v2.x" the brief asks about is now superseded: v3 is a from-scratch Rust rewrite** (`pbdems2` backend, `PyO3` + Polars) released 2026-10-14.
- **Architecture.** Rust workspace: `crates/awpy` (core: io, entity system, parser, name tables), `crates/awpy-proto` (prost-generated CS2 protobufs), `crates/awpy-python` (PyO3 bindings publishing the `awpy` wheel), `crates/awpy-dev` (dev CLI). Workspace deps: `pbdems2 = "0.4"`, `prost 0.14`, `serde`, `anyhow`; `rust-version = 1.88.0`. Python layer = thin: `schema.py` (friendly→engine property map), `data.py` (map-asset cache), `map_control.py` (Python-side model), `plot.py`, `cli.py`. Source: `Cargo.toml` + tree of clone, 2026-10-15.
- **Data exposed (Demonstrated, from README datasets table + `docs/changelog.md`).** Cached datasets `rounds`, `kills`, `damages`, `bomb`, `grenades` (per-tick trajectories), `fires`, `smokes` (position + thrower + `[start_tick,end_tick]`), `shots` (incl. clip/inaccuracy/scoped), `blinds` (thrower, blinded player, duration), `item_events`, `stats` (KAST/ADR/trades/clutches/utility), `round_economy` (eco/force/full), `players`, `chat`, `convars`, plus:
  - `demo.events.<any_game_event>` — generic event access; `demo.events.names` lists events present.
  - `demo.ticks(props)` — **one row per player per tick for arbitrary networked properties**; accepts friendly aliases *and* raw engine names (`m_iHealth`, `m_iTeamNum`) per `docs/datasets.md:562-569`; `players_only=False` yields one row per (tick, entity) with `class_name`, `entity_id`, `entity_serial`.
  - `snapshots(ticks=/every=/seconds=/events=/start_tick/end_tick)` — per-player state incl. **eye angles** (`pitch`/`yaw` from `m_angEyeAngles[0..1]`), position, velocity (+ derived speed), health, armor, economy, loadout, `is_reloading`, `is_blinded` (from `m_bFlashing`).
  - `header`, `tick_rate`, `tick_to_seconds()`/`seconds_to_tick()`.
  - Map data: `VisibilityChecker(map).is_visible(a,b)` / `is_occluded`, `NavMesh(...).find_area/find_path`, `awpy.data` asset cache, `awpy.map_control(..., method="raycast"|"vision"|"reachability")`.
- **Programmatic integration.** `pip install awpy` (wire-compatible wheels only — no Rust toolchain needed), `import awpy`; plus a Rust crate (`awpy`), and a CLI (`awpy info|kills|stats|get|versions|maps|clear`, `--json` output). Docs: `https://awpy.readthedocs.io` (autodoc off the compiled extension).
- **Open/closed + license.** Open source, **MIT** (GitHub `license.spdx_id = MIT`; PyPI `license_expression = MIT`).
- **Linux compat.** **Demonstrated.** Prebuilt manylinux wheels for `x86_64` and `aarch64`, CPython 3.11–3.15 (`awpy-3.0.0-cp314-abi3-manylinux_2_17_x86_64...whl` etc. from the PyPI release listing). Requires Python ≥3.11 and `polars>=2.0,<3`.
- **Reusability.** High for a Python-first local pipeline: the whole "demo → tidy tables" step is one dependency, and `ticks()`/`events` act as the escape hatch for anything not pre-built.
- **AI real vs marketing.** No AI claims in the package itself. What *is* real and verifiable: geometry-based LOS (`VisibilityChecker` over `.mesh` collision tri meshes with a BVH), nav-mesh graph routing, and a map-control model with three explicit methods and tunable parameters (`MapControlParams`: `fov=90°`, `smoke_radius=144`, `smoke_height=60`, `fire_radius=150`, `contest_margin=200`) — parameters exposed, not hand-waved. What is **not** validated: visibility *fidelity*. `tests/test_visibility.py` only checks a synthetic single-wall quad mesh; `tests/test_ground_truth.py` validates **scoreboard stats** against csstats/FACEIT/HLTV, **not** visibility. So "is this in-game LOS?" is unproven → see §11.
- **Unsolved problems.** (a) No `m_bSpotted`/`m_bSpottedByMask` in the snapshot schema or any dataset; only `CcsUsrMsgProcessSpottedEntityUpdate` (message type 325) is *decoded* in `crates/awpy/src/demo/decode.rs:37` — no documented dataset/event name for it, so radar-spot state is at best reachable via raw `events`/`ticks` (`[INFERENCE]`, untested). (b) `VisibilityChecker` explicitly models static geometry only — "does not model smokes, moving doors, or bullet penetration. Player positions are not eye positions" (`docs/visibility.md:35-37`); smoke occlusion therefore exists **only** in `map_control`, not in the general LOS API. (c) Map assets (`geometry.zip`, `navs.zip`, `images.zip`) are downloaded from GitHub releases of `pnxenopoulos/awpy-data` (`DATA_REPO = "pnxenopoulos/awpy-data"`, cache in `~/.awpy`) → a **network dependency**, versioned per CS2 `ClientVersion`; issue #526 (closed 2026-10-08) records a 403 from the older `awpycs.com` host. (d) Multipart demos supported but "splits during live play are not supported". (e) No CS:GO demo support at all (deliberate). (f) Protos track CS2 build 2000924 while CS2 build 2000932 shipped 2026-10-15 (`SteamTracking/GameTracking-CS2` commit log) — expects patch churn.

## 2. pbdems2 (pnxenopoulos/pbdems2) — the game-neutral Source 2 core under awpy

- **What it does.** Rust crate of "game-neutral Source 2 PBDEMS2 demo parsing primitives": file structure, packet messages, serializers/field paths, string tables, entities, playback + a `DemoAdapter` seam that game-specific parsers (awpy, `boon` for Deadlock) implement. Ships a docs.rs guide (`pbdems2::guide::{file_structure, packet_messages, serializers, string_tables, entities, playback}`).
- **CS2 demo support.** **Demonstrated indirectly** — it has no CS2 protobufs/field decoders itself; awpy adds "CS2 protobufs, field decoders, and name tables" on top of the shared core (awpy README line 22).
- **Maintenance status.** **Very active.** crates.io latest `0.4.0` published **2026-10-12T22:29Z**; versions 0.3.0→0.4.0 shipped 2026-08-30 → 2026-10-12 (8 releases in ~6 weeks); commits 2026-10-13 ("update tests"), 2026-10-12 ("0.4 for pbdems2"); 1,685 total downloads. License **MIT** (per crate version metadata; crate-level field is unset).
- **Architecture.** Library crate, `DemoAdapter` trait + protobuf-agnostic PBDEMS2 reader; downstream crates own generated protos and domain models. `docs.rs/pbdems2/latest/pbdems2/guide/index.html` (read 2026-10-15).
- **Data exposed.** Low-level: packets, messages (incl. `svc_UserCmds`, `CSVCMsg_PacketEntities`), string tables/instance baselines, entity field paths, playback/keyframes.
- **Programmatic integration.** `cargo add pbdems2` + implement `DemoAdapter`. docs.rs for API.
- **Open/closed + license.** Open, **MIT**. Linux: pure Rust, no platform constraint.
- **Reusability.** High *if building in Rust*; irrelevant if staying in Python (awpy already wraps it). Also shared with a Deadlock parser → format work is amortised across two games.
- **AI real vs marketing.** No AI.
- **Unsolved problems.** Young API (0.x, churning weekly) — pin exact versions; no CS2 semantics of its own; undocumented compatibility guarantees with future CS2 builds beyond awpy's CI proto diff.

## 3. demoparser2 (LaihoE/demoparser) + Python-/node-bindings + WASM

- **What it does.** Rust CS2 replay parser exposed as a *query* API (SQL-like, non-streaming): `DemoParser(path).parse_event(event, player=[props], other=[props])` and `parse_ticks(props)` returning DataFrames/JSON; plus `parse_grenades`, `parse_player_info`, `parse_voice`-family and item-skin helpers, in Python (PyO3), NodeJS (napi), and WASM builds.
- **CS2 demo support (verified how).** **Demonstrated.** Repo description "Counter-Strike 2 replay parser for Python and JavaScript"; CS2 protos bundled in-tree (`src/csgsoproto/src/protobuf.rs`, e.g. `CsvcMsgUserCommands`, `CsvcMsg_UserCommands.delta_data`); e2e tests assert real props (`parser/src/e2e_test.rs` lists `CCSPlayerPawn.m_bSpotted`, `.m_bSpottedByMask`, `CCSPlayerPawn.m_bResumeZoom`, …). Also note the README itself documents Dota-2 format similarity; **no CS:GO support** — the old CS:GO effort lives in the abandoned `LaihoE/Python-demoparser` (last push 2023-07-30, 37★).
- **Maintenance status.** **Active, but slower cadence than awpy/demoinfocs.** PyPI `demoparser2` latest **0.42.0 (2026-08-08)**; Git tags `v0.42.0`/`v0.42.01` 2026-08-08; repo `pushed_at` **2026-10-05**, 733★, 104 forks, **23 open issues**, 160 issues total. Commits 2026-10-05: "fix: decode 14-bit demo entity handles (#363)", "Handle invalid UTF-8 in game event string values (#364)", "fix: handle repeated econ item custom names (#361)". npm `@laihoe/demoparser2` = 0.42.0 (2026-08-08). **WASM package `demoparser2` on npm is stale at 0.15.0 (2023-12-04)** while the Rust repo kept moving → the browser path is effectively frozen; a separate `LaihoE/demoparser-wasm-demo` (2025-06-10) exists as a demo.
- **Architecture.** Rust core (`src/parser`), hand-rolled two-pass decode: `first_pass/prop_controller.rs` allocates synthetic prop IDs (`USERCMD_VIEWANGLE_X = 100000022`, …) for non-networked data; `second_pass/collect_data.rs` resolves custom props (`find_spotted`, `find_my_inventory`, …); `second_pass/parser.rs` decodes `CMsgServerUserCmd` including the CS2 `delta_data` codegen-delta encoding (`usercmd_delta.rs`, `apply_delta`, sanitize + protobuf-delta merge). Bindings: PyO3 (PyPI), napi (npm), wasm-bindgen (npm, stale).
- **Data exposed.** Very broad, *queryable by arbitrary prop path* (`parse_ticks(["CCSPlayerPawn.m_bSpotted"])` style is exercised by tests; friendly aliases map to paths in `parser/src/maps.rs`, e.g. `spotted → CCSPlayerPawn.m_bSpotted`, `approximate_spotted_by → CCSPlayerPawn.m_bSpottedByMask`). Player data includes `X/Y/Z`, `pitch`/`yaw` (`m_angEyeAngles[0..1]`), `spotted`, `approximate_spotted_by`, `in_buy_zone`, `aim_punch_angle`, weapon/glove/skin detail, aggregate per-round stats; **usercommands block**: `usercmd_viewangle_x/y/z`, `usercmd_buttonstate_1..3`, `usercmd_forward_move`, `usercmd_left_move`, `usercmd_impulse`, `usercmd_mouse_dx/dy`, `usercmd_left_hand_desired`, `usercmd_weapon_select`, `usercmd_input_history`, `usercmd_subtick_moves`, `usercmd_consumed_server_angle_changes` (README field tables, repo @ 2026-10-15).
- **Programmatic integration.** `pip install demoparser2` (≥3.8, wheels manylinux x86_64/aarch64, macOS x86/arm, win32/amd64, CPython 3.7–3.14); `npm i @laihoe/demoparser2`; WASM (stale). Examples dir + "scuffed documentation" folder + Discord.
- **Open/closed + license.** Open, **MIT**. Linux: **Demonstrated** (manylinux wheels; author's own benchmark ran on Ubuntu 20.04).
- **Reusability.** High for a *local* pipeline: fastest path to arbitrary per-tick props and the only mainstream Python parser exposing **usercmd/input** and **spotted masks** without dropping to a streaming API.
- **AI real vs marketing.** No AI claims. Performance claim in README ("50 demos, 4.6 GB, 6.14 s on a 12-core desktop = 749 MB/s; ThinkPad T4 328 MB/s") is plausible and *substantiated in-repo* by `PARSE_SPEEDUP_BASELINE.md`, a measured harness (`src/parser/src/bin/parse_bench.rs`, median of 5, byte-identical output checksum, 333 tests green) whose headline table claims live metrics of **~3.7 s / 0.65 s (MT) on a 430 MB Navi-vs-Mongolz Nuke demo, vs 10.95 s / 2.24 s baseline (~2.5–3.8× ST/MT)** — i.e. the repo is *faster than the README benchmark implies*, single-threaded. Treat numbers as machine-specific but real.
- **Unsolved problems (all from open/closed issues, dates = created).** CS2 patch breakage is the dominant theme: **#365** string-table updates after first FullPacket dropped (open, 2026-10-12); **#362** entity handles masked with 0x7FF instead of 0x3FFF — players with pawn index >2047 broken (fixed 2026-09-30; fix landed as #363 above); **#359** `IllegalPathOp` on parseEvent/parseTicks with a deathmatch GOTV demo (open, 2026-09-26); **#358** bots unresolved in events/ticks — `user_*` null, bots missing (open, 2026-09-26); **#345** `usercmd_subtick_moves` missing from `parse_ticks()` output in 0.42.0 (open, 2026-08-10); **#340** newer demos use `CMsgServerUserCmd.delta_data`, usercmd data lost (closed 2026-07-11 — the `usercmd_delta.rs` decoder is the fix); **#342** buttons no longer in output (closed 2026-07-20); **#339** entity-stream desync → `EntityNotFound` on a PRACC-server demo (open, 2026-07-08); **#330** `UnknownDemoCmd(34)` on **FACEIT demos** after a May-2026 CS2 patch (open, 2026-05-22); **#329** `IllegalPathOp` on a **Valve POV demo** (open, 2026-05-21); **#321/#325** `EntityNotFound` after patches 14152–14155 (closed via 0.41.2, 2026-04-21); **#318** "Critical: missing rounds and incorrect T/CT mapping" (closed 2026-03-31); **#317** `inferno_startburn` entity id ≠ `parseGrenades` id (open, 2026-03-30); **#302** POV demo: part of data `None` (open 2025-12-15); **#287** "POV demos have null values for grenades and detonations" (closed 2025-09-08); **#297** no documented sound events / `sound_lvl` (open, 2025-11-20); **#299** bomb entity coordinates question (open, 2025-11-24). Practical conclusion: **pin versions, keep a demo corpus for regression, and expect FACEIT/POV demos to need special handling.** Also: `approximate_spotted_by` is lossy by construction — see the dedicated bullet below.
- **Grenade lifecycle/perf notes.** `parse_grenades(grenades=True, ...)` returns per-tick trajectory rows with `thrower_steamid` and `entity_id` (docs/python README L132-142); inferno id-matching bug open (#317). Grenade/perf issues over time: #261 "New parse grenades function" (2025-03-09), #276 toggleable grenades (2025-05-29), #279 improve header parse performance (2025-06-06), #273 Python perf optimisation (2025-05-11), #248 performance regression in 0.36.0 (2025-02-17), #172 memory error on `round_end` for some demos (2024-05-29), #154/#145 (2024). Memory: parsing is per-call over the whole file (no streaming) → peak memory is a design constraint for big corpora.
- **`approximate_spotted_by` failure modes are silent, and narrower than "16 bits" suggests** (`second_pass/collect_data.rs:790-812` + `game_events.rs:244-251`): (a) `find_spotted` only accepts the parent prop as a single `Variant::U32`, so it reads **one** 32-bit word — the second word (`m_bSpottedByMask.0001`, controller slots 32–63) and bits 16–31 of word 0 are **never** inspected; (b) the loop is `for i in 0..16` and maps bit `i` → controller entity id `i+1` via a linear scan, so a bit whose controller cannot be resolved is **silently dropped** (indistinguishable from "nobody spotted"); (c) a resolvable controller with no steamid pushes a literal `0` into the returned list. Net: this column is a *corroborator for the first 16 controller slots*, and its negative result must not be read as ground truth. In a 5v5 (10 player controller slots) the word cutoff and the `0..16` loop are *not* the practical loss — failure mode (b) is: a dropped bit is indistinguishable from "no spotters", so the convenient column **cannot falsify anything**, and any correlation test must take bit-level truth from the awpy dotted path in the same run. The raw mask words are not otherwise exposed by name (the prop name is mapped to `PropType::Custom`).

## 4. demoinfocs-golang (markus-wa/demoinfocs-golang) — battle-tested Go parser, now v6-alpha

- **What it does.** Streaming, event-handler-based parser for CS2 **and** CS:GO demos: game events, game-state tracking (players/teams/grenades/ConVars), grenade trajectories, raw entities & sendtables, **all net-messages**, chat/console, matchmaking ranks (official MM demos), full POV support, and **live CSTV+ broadcast parsing**.
- **CS2 demo support (verified how).** **Demonstrated.** Repo description "A Counter-Strike 2 Demo Parser for Go"; CS2 sendtables/reader (`sendtables/sendtablescs2/reader.go`), CS2 usermessage handlers, CS2 proto set in `pkg/demoinfocs/msg` + `proto/` (`netmessages.proto`, `cstrike15_usermessages.proto`), and a CS2-specific test corpus. README names 15+ production consumers (HLTV, PGL, FASTCUP, ESPORTAL, scope.gg, noesis.gg, refrag.gg, esportslab.gg, cs2lens.com, …). ⚠️ The README's acknowledgement line "awpy — A wrapper for the Golang parser in Python" is **outdated** (that was awpy v1/v2's design; awpy 3.x uses Rust/`pbdems2`) — a good example of prose drift vs. reality.
- **Maintenance status.** **Very active, and mid-major-version.** Releases: `v6.0.0-alpha.1` (2026-10-11, prerelease), `v6.0.0-alpha.0` (2026-08-31), `v5.2.0` (2026-04-21), `v5.1.4` (2026-04-10), `v5.1.3` (2026-04-04), `v5.1.2` (2026-01-23); repo `pushed_at` **2026-10-14**, 1,069★, 150 forks, **7 open issues / 261 total**. Commits 2026-10-14: "fix: keep ServerClasses obtained before the header live", plus a `refactor/concrete-types` merge. **v5 remains maintained on a `v5` branch** (stated in the v6 alpha notes).
- **Architecture.** Pure Go, modular `pkg/demoinfocs` (parser, game_state, net_messages, datatables, s2_commands, option/config) + `pkg/demoinfocs/common` (Player/Team/Equipment/GrenadeProjectile), `sendtables` (+ `sendtablescs2`), `events`. **Streaming + callbacks** (`parser.RegisterEventHandler`, `parser.ParseToEnd`, `parser.Seek`) — the opposite model to demoparser2's query API. v6 alpha adds `ParserConfig.NetMessageDecryptionKey`, warning types, concrete-typed refactor, Go 1.27 requirement, `/v6` import path.
- **Data exposed.** Events (kills, shots, round start/end, footsteps, `PlayerSpottersChanged`, `PlayerButtonsStateUpdate`, bomb, grenades, inferno), game state (positions incl. `PositionEyes()`, velocity, weapons, ammo, money, teams), grenade projectiles, entities + full data tables, all net-messages (`RegisterNetMessageHandler`, incl. `CSVCMsg_EncryptedData`), chat/console (**encrypted MM chat now decryptable**), matchmaking ranks, CSTV+ live.
- **Programmatic integration.** `go get .../v5/pkg/demoinfocs` (or `/v6` alpha); WASM for JS via `markus-wa/demoinfocs-wasm` (that repo last pushed 2023-06-01, 13★ → **stale**). Examples in-repo: print-events, entities, nade-trajectories, net-messages, broadcasts.
- **Open/closed + license.** Open, **MIT**. Linux: **Demonstrated** (pure Go, CI on Linux, used by Linux-hosted services).
- **Reusability.** Highest of all for *streaming/enterprise* needs and the only parser with (a) official-MM **demo decryption key** support and (b) live CSTV+ parsing. For a Python local-first pipeline it means a Go binary/HTTP sidecar.
- **AI real vs marketing.** No AI. Performance claims are supported by a real benchmark (`BenchmarkDemoInfoCs`): v6 alpha.1 vs alpha.0 — "~12% faster, ~19% less memory, ~3% fewer allocs/op". v6 alpha.1 notes also include a rare, credible *validation* claim: `PlayerHurt.HealthDamageTaken` now matches the game's own damage stats in 7,223 / 7,230 player-rounds across a **41-demo corpus** (the 7 misses being `player_hurt` events GOTV dropped) — that is Research-supported ground-truth behaviour, and it flags that ADR computed this way will be ~1% higher than HLTV's (use raw `dmg_health` to reproduce HLTV).
- **Unsolved problems.** (a) **PVS/entity-lifecycle bugs that directly affect visibility work: #728** "entities that leave the PVS stay active, re-entry never reports EntityOpEntered" (open, 2026-10-14) and **#714** "POV demos: entities that left the PVS aren't destroyed when their index is reused" (open, 2026-10-12). (b) `SpottedBy` fragility: **#629** "SpottedBy crashes because of nil pointer dereferences" (closed 2026-01-17); source doc comments repeat "This is NOT 'Line of Sight' / FOV… May not behave as expected with multiple spotters" (`common/player.go:247-285`, `game_state.go:555-576`). (c) No raycasting/visibility helper of any kind in `pkg/` (verified by grep) — only pointers to engine `TraceRay`. (d) Sendtable field-path collisions: **#673** "fields sharing a name under different send_node collapse last-wins — `m_vecVelocity` unreachable on player …" (closed 2026-08-27). (e) CS2 patch churn: **#652** panic on latest demos (closed 2026-04-21), **#645** AnimGraph-2 demos did not parse (closed 2026-04-09), **#610** demos after the 2025-10-15 update failed (closed 2025-10-15), **#634/#598** memory-usage reports (closed 2026-01-26/2025-06-05). (f) POV gaps: grenade projectile data missing (`#555`, 2024-07-31), inferno re-creation after leaving PVS can't be linked (in-code comment, `datatables.go:1280-1282`), `PositionEyes()` panicked on Source 2 (`#649`, closed 2026-04-16). (g) Encrypted-net-message path is **Experimental by the author's own admission**: "no encrypted CS2 demo in the test suite yet … a wrong key currently fails the parse instead of just warning" (v6.0.0-alpha.1 notes).

## 7. Valve/Source 2 side: official parser status, proto & schema sources, demo file provenance

- **Is there any official Valve CS2 parser or schema?** **No parser — but yes, an official pipeline for schema/protos.** Valve's historical C++ tool (`ValveSoftware/csgo-demoinfo`) is CS:GO-only and dead since **2017-12-19**. For CS2, the de-facto authoritative artifacts are the dumps in **`SteamTracking/GameTracking-CS2`** (moved from `SteamDatabase/`): `Protobufs/` (game protobufs, incl. `netmessages.proto`, `cstrike15_usermessages.proto`) and `DumpSource2/schemas/**/*.h` (the networked class schema). Status: **extremely active** — commits dated **2026-10-15** ("2000932"), 2026-10-14 ("2000931"), 2026-10-13 ("2000930"); 1,011 commits, 971★, 131 forks. Every serious parser (awpy 3.x with `scripts/sync-protos.sh --check`, demoparser, demoinfocs, demofile-net via Source2Gen) is downstream of these dumps. **This repo, not any parser, is the ground truth for "what fields exist".**
- **`ValveResourceFormat` (Source2Viewer).** An all-in-one **asset** tool: browse VPK archives, decompile maps/models/materials/textures; 2,507★, MIT, very active (release **20.0** 2026-08-17; repo pushed 2026-10-14). **It does not parse `.dem`.** Primary evidence: issue **#1122** "Support for `.dem` replay files" (opened 2026-03-26) was **closed as unsupported** by maintainer **xPaw** ("There are already separate demo parsers for S2 games. Unless you're willing to put the work in yourself to add support for them in this project, then I'm gonna close this issue"), and later labelled **"Unsupported File"** (2026-10-08). → VRF is relevant to *map geometry/radar/model assets* (rendering a 2D/3D viewer, extracting collision or nav data), **not** to demo decoding. Verdict for the parser layer: **ignore; integrate only as an asset supplier.**
- **Demo file provenance (`.dem`, `.dem.bz2`, `.dem.info`) — status 2026.** Valve MM/Premier demos are delivered as `replay<N>.valve.net/730/<id>_<id>.dem.bz2` (undocumented host pattern) or, more reliably, resolved by the client itself via `csgo_download_match <CSGO-… share code>` / Steam `steam://rungame/730/...`; the accompanying **`match730_*.dem.info` sidecar holds the decryption key** for encrypted net-messages. `stats.steampowered.com` is Steam *stats/profile* infrastructure, **not** the replay CDN. This is now table stakes for tooling, and is **Demonstrated in code**, not just folklore: `demoinfocs-golang/v6` added `ParserConfig.NetMessageDecryptionKey` + `MatchInfoDecryptionKey(b []byte)` ("set it to the key from the `match730_*.dem.info` file", v6.0.0-alpha.1 notes, 2026-10-11), because **CS2 made chat messages encrypted in official matchmaking demos since the Sept-2026 update**; `player.go`/`option.go` comments and `events.WarnTypeMissingNetMessageDecryptionKey` confirm the failure mode. CS Demo Manager's docs describe the same `.info` semantics, and `demofile.dev` exposes `extractPublicEncryptionKey`. → **Any local-first pipeline that wants chat/voice from official MM demos must handle `.dem.info`.**
- **Hex/legacy note.** The brief's "`stats.steampowered.com` / hex-format demos" maps onto nothing usable in 2026: CS:GO-era Valve replay URLs and the CS:GO `demoinfogo` path are **Infeasible/dead** for CS2 (CS2 uses PBDEMS2 + protobuf/bzip2 containers, and CS2 proto dumps are public). Treat "hex demo" as folklore unless a specific artifact can be produced.

## 8. Fog of War: what the demo actually contains, and what parsers expose

This is the crux for a coaching product ("what could the player see / know?"). Findings, each with evidence:

**8.1 Per-tick "spotted" state exists in the networked schema (not a parser invention).**
`SteamTracking/GameTracking-CS2` @ master, read 2026-10-15, `DumpSource2/schemas/client/EntitySpottedState_t.h`:
```c
class EntitySpottedState_t { bool m_bSpotted; uint32[2] m_bSpottedByMask; };
```
and `C_CSPlayerPawn.h` line 60: `EntitySpottedState_t m_entitySpottedState;` (line 99: `QAngle m_angEyeAngles`). So **both the boolean and the 64-bit by-mask are CS2 networked state** — Demonstrated.

**8.2 Who exposes it.**
- **demoparser2: yes, directly.** `spotted` (`CCSPlayerPawn.m_bSpotted`) and `approximate_spotted_by` (`CCSPlayerPawn.m_bSpottedByMask`) are first-class field names (`parser/src/maps.rs:1071-1072`), unit-tested (`parser/src/e2e_test.rs:3230-3395`, `node/tests/parser.test.js:894-897` with fixture data), and resolved by `find_spotted` → `steamids_from_mask`, which walks mask bits **0..15**, mapping bit `i` → controller id `i+1` → SteamID (`second_pass/collect_data.rs:790-812`). **Limitations are structural:** 16-bit window, controller-slot interpretation, one mask value shared for all spotters, and the author's own naming ("approximate"). **Demonstrated + Experimental.**
- **demoinfocs-golang: yes, with an explicit warning.** `Player.IsSpottedBy(other)` / `HasSpotted`, `Participants.SpottersOf/SpottedBy`, and an event `PlayerSpottersChanged` dispatched when `m_bSpottedByMask.0000/0001` updates (`datatables.go:848-862`). Bit math: `clientSlot := other.EntityID - 1`, two 32-bit words (`common/player.go:247-285`). The **documented caveat is repeated four times in source**: *"This is NOT 'Line of Sight' / FOV — look up 'CSGO TraceRay' for that. May not behave as expected with multiple spotters."* Also was crash-prone until 2026-01-17 (#629). **Demonstrated (mechanics) / Plausible-untested (fidelity).**
- **awpy 3.x: no first-class exposure.** No `spotted` column in `SNAPSHOT_PROPERTIES`/datasets (grep of `crates/awpy/src`, `python/awpy/schema.py` → only `CcsUsrMsgProcessSpottedEntityUpdate` decoded as message type 325 in `demo/decode.rs:37`). Because `ticks(props)` accepts **raw engine field names** (`docs/datasets.md:562-569`) it is *likely* that `demo.ticks(["m_bSpotted", "m_bSpottedByMask"])` works — **Plausible-untested `[INFERENCE]`; verify on a real demo before designing around it.**
- **demofile-net (C#): schema-generated access** to `EntitySpottedState_t` (`[INFERENCE]` on member naming; schema verified in 8.1).

**8.3 GOTV vs POV demos — this is where naive visibility work breaks.**
- A POV (client-side) demo records **one client's PVS-filtered entity stream**. That is why demoinfocs documents grenade `Projectile` as nil "in POV demos for entities outside of the recording player's PVS" (`events/events.go:229-231`), why POV infernos re-created on PVS re-entry "can't be linked" (`grenade_event_projectile_demo_test.go:122-125`), why POV entity-index reuse is still broken (#714, open 2026-10-12), why PVS leave/re-enter never reports `EntityOpEntered` (#728, open 2026-10-14), and why demoparser2 has repeated POV holes (#287, #302, #329). **Consequence:** in a POV demo the *absence* of an entity is itself a visibility signal (a genuinely player-centric view), but the parser APIs are not designed to hand you that cleanly — you get gaps and nulls.
- A **GOTV/CSTV+ demo is a spectator client's stream**. The spotting state you read (`m_bSpotted`/`m_bSpottedByMask`) is replicated to *that* client (the relay/camera), not to each player. Therefore **the mask in a GOTV demo must not be read as "player X could see player Y"** — this is the practical reading of demoinfocs' "may not behave as expected with multiple spotters" and demoparser2's "approximate" label. `[INFERENCE]` (well-supported by the spectating-client architecture + the two parsers' own disclaimers, but **no primary source states it explicitly**). Any product relying on this must validate against ground truth (e.g., manual annotation of a handful of rounds, or cross-checking with the awpy geometric LOS for known sightlines).
- Also relevant: the client-facing usermessage **`CS_UM_ProcessSpottedEntityUpdate` (id 325)** — the radar/spotting update pushed to the client — exists in every proto set (awpy `CcsUsrMsgProcessSpottedEntityUpdate`, demoinfocs `msg.CCSUsrMsg_ProcessSpottedEntityUpdate` with `entity_idx`, `class_id`, `origin_*`). demoinfocs registers a decoder for it but **does not dispatch a public event** (grep of `pkg/demoinfocs` finds no event type for it); awpy decodes it into its user-message path. → radar-visible state is *available in principle* but **not productised**; `[INFERENCE]` for how to reach it cleanly.

**8.4 View angles / eye positions — available; caveats.** Eye angles: awpy snapshots (`pitch`/`yaw` ← `m_angEyeAngles[0..1]`, `schema.py:29-30`), demoparser2 (`pitch`, `yaw`), demoinfocs (`PositionEyes()`; a Source-2 panic was fixed 2026-04-16, #649). **awpy's `VisibilityChecker` does *not* use eye height** — docs say "Player positions are not eye positions", so a naive LOS call from recorded positions silently uses feet/centre coordinates. FOV: awpy's `map_control(method="vision")` applies a horizontal FOV (`fov=90` default, ignores pitch, falls back to unlimited FOV if yaw is missing).

**8.5 usercmd / input data — partially available.** Only **demoparser2** exposes input at prop level: `usercmd_viewangle_x/y/z`, `usercmd_buttonstate_1..3`, `usercmd_mouse_dx/dy`, `usercmd_forward_move`, `usercmd_left_move`, `usercmd_impulse`, `usercmd_weapon_select`, `usercmd_input_history`, `usercmd_subtick_moves`, `usercmd_consumed_server_angle_changes` (`parser/src/maps.rs:213-260`, `first_pass/prop_controller.rs:57-62` synthetic prop ids). Critical history: newer CS2 demos send `CMsgServerUserCmd.delta_data` (codegen-delta encoding) — demoparser2 lost usercmd data entirely until #340 was fixed on 2026-07-11 by writing its own delta decoder (`second_pass/usercmd_delta.rs`). Buttons disappeared in 0.4x (#342) and `usercmd_subtick_moves` is **still missing in 0.42.0** (#345, open 2026-08-10). demoinfocs exposes a `PlayerButtonsStateUpdate` event, derived from `CSVCMsg_UserCommands` with a legacy fallback for demos lacking them (`datatables.go:864`); player-community question #587 ("reconstructing keyboard and mouse inputs") closed without the full usercmd prop surface. awpy: no usercmd dataset (only protobuf types present). → **If input reconstruction (mouse movement, jump timing, counter-strafing) is a coaching feature, demoparser2 is the only sane entry point today, with an open bug on subtick moves.**

**8.6 Smoke / grenade occlusion.** No parser models occlusion for you. Best available building blocks: **awpy** — collision `.mesh` + BVH (`VisibilityChecker`) and, at the map-control layer only, active smokes as spheres (`smoke_radius=144`, `smoke_height=60`) + fire radius for the reachability model (`crates/awpy-python/python/awpy/map_control.py`, `docs/map_control.md`); the LOS checker itself is documented as **static geometry only — no smokes, moving doors, or penetration**. **demoparser2** — per-tick grenade trajectories with `entity_id` + thrower (`parse_grenades`) plus smoke/fire events, so you can reconstruct smoke spheres yourself; note the open id-mismatch bug for `inferno_startburn` vs `parseGrenades` (#317). **demoinfocs** — grenade projectile tracking + `InfernoStart/Expired`, `SmokeStart` events with known POV/PVS linking gaps.

## 10. Best foundation for a local-first pipeline — verdict with evidence

**Primary: awpy 3.x (Python + Rust, Polars).** Reasons, all Demonstrated: (1) it is the *only* package found that ships the analysis primitives a coaching product needs out of the box — cached round/kill/damage/grenade/smoke/fire/flash/economy/stats datasets **plus** per-tick state **plus** map collision geometry, nav meshes, and a map-control model, all in one MIT-licensed dependency with Linux wheels and no Rust toolchain; (2) its API is query-shaped (`demo.load(...)`, `demo.ticks(props)`, `demo.events.<name>`) which maps cleanly onto a local cache/warehouse (Polars → Parquet) rather than a streaming handler graph; (3) it is the most actively maintained of the three (release 2026-10-14, commits 2026-10-15, active issue triage with fixes shipped same-week, e.g. #526, #524); (4) map geometry is bundled/versioned per CS2 `ClientVersion` (`awpy-data` releases every few days: 2000930 on 2026-10-09), which is exactly what geometric fog-of-war needs; (5) it is CS2-only by design, so there is no CS:GO legacy ballast.

**Also integrate (not replace): `demoparser2`.** It is the only mainstream Python entry point that exposes **`m_bSpotted`/`m_bSpottedByMask` and the usercmd/input block** at prop level (`spotted`, `approximate_spotted_by`, `usercmd_*`), and its measured throughput is high (in-repo 430 MB demo: ~0.65 s multi-threaded, ~3.7 s single-threaded; README: 749 MB/s on a 12-core desktop). Practical pattern: awpy for the canonical datasets/geometry, demoparser2 for the two prop families awpy lacks. Both are MIT, both ship manylinux wheels, both are query-shaped → they compose without architecture conflict. Cost: a second parser means a second patch-churn surface (demoparser2 has 23 open issues and repeated `EntityNotFound`/`IllegalPathOp` reports across 2026), so pin both and keep a demo corpus for regression.

**Integrate conditionally: `demoinfocs-golang` v5** if you need (a) **official matchmaking chat/voice decryption** from `match730_*.dem.info` (`MatchInfoDecryptionKey` — note the decrypt path is untested upstream), or (b) **live CSTV+ broadcast** parsing. Both are unique to it; neither is Python-native, so it implies a Go sidecar/binary. Prefer the **v5 stable** line (v5.2.0, 2026-04-21) over the v6 alpha for production (v6.0.0-alpha.1 has open PVS entity-lifecycle bugs #714/#728).

**Reject:** awpy v2.x (superseded 2026-10-14 by the Rust rewrite), `saul/demofile` (archived, CS:GO), `ValveSoftware/csgo-demoinfo` (dead since 2017, CS:GO), `demostf/demos.tf` (TF2), `ValveResourceFormat` *as a demo parser* (issue #1122 closed as unsupported), and the non-existent `jsdemoparser` / `cs2-demoinfodb` / `democli`.

**Confidence.** Version/date/license/activity facts: high (machine-readable primary sources). API-surface facts: high (source + tests). Visibility-state semantics (especially GOTV vs per-player spotting): **medium** — the artifacts are real, but no primary source validates them as in-game LOS, and the two parsers that expose them explicitly disclaim LOS/FOV semantics.

## 11. Cross-cutting notes (gaps, duplicate work in this cluster, follow-ups)

1. **`m_bSpottedByMask` semantics is the highest-value unresolved question in this slice.** Both exposing parsers disclaim it (demoinfocs: "NOT Line of Sight / FOV"; demoparser2: "approximate"), the demoparser2 mapping is a 16-bit/controller-slot heuristic, and my `[INFERENCE]` that a GOTV demo's spotted state reflects the spectator client rather than each player is unverified. **Cross-checked with `DemoDataFogOfWar` (2026-10-15): no paper/tool validates the mask against geometric LOS; the closest audit is Leetify's "Enemy (actually) spotted" (2020-10-04), which measured 0–500 ms radar lag, part-of-model/angle dependence, a post-LOS "shadow", and pre-event AWPer shots — and abandoned server radar events for its own geometry check.** Verdict therefore hardened to **corroborator only, never the label**. Agreed de-risk test: correlate mask rising edges vs geometrically computed per-player visibility on one GOTV demo. That slice owns prior-art tooling; this slice owns parser-side data availability. If the mask is read through awpy, the exact prop string is `m_entitySpottedState.m_bSpottedByMask.0000/.0001` (nested path required — §8.7); through demoparser2 it is `approximate_spotted_by`, one call.
2. **Map-geometry pipeline is split across two slices.** The `.mesh`/`.nav` formats, `awpy-data` release semantics, and mesh quality/completeness (holes, doors, penetration, multi-level maps) belong to `EcosystemSurvey.MapGeometry`; I verified only that awpy consumes them (`crates/awpy-python/python/awpy/data.py`, assets `geometry.zip`/`navs.zip`/`images.zip`, cache `~/.awpy`, `DATA_REPO = pnxenopoulos/awpy-data`). **Do not duplicate**: one owner for "does the collision mesh faithfully represent shootable geometry".
3. **"No ground-truth visibility validation exists"** — awpy's visibility tests are synthetic (single wall quad) and its ground-truth suite validates *scoreboards* only. If the product's core claim is "what you could see", building a labelled validation set is *greenfield work*, not a library-selection decision. Flag to Main as a research/product gap.
4. **Patch churn is the operational risk, not parser choice.** Evidence: demoparser2 (5+ patch-breakage issues in 2026, incl. FACEIT `UnknownDemoCmd(34)` and POV `IllegalPathOp`), demoinfocs (#652, #645, #610 panics/failures after CS2 updates), awpy (#524 default-tickrate bug, #526 asset 403, protos pinned to build 2000924 while CS2 shipped 2000932 on 2026-10-15). Any pipeline needs version pinning + a regression corpus + a "parser canary" job on each CS2 update.
5. **Schema/proto source of truth is `SteamTracking/GameTracking-CS2`** (daily commits; `Protobufs/` + `DumpSource2/schemas/`), consumed by every parser here. Treat it as the reference when a parser's field name disagrees with reality — it resolved the `EntitySpottedState_t` question directly.
6. **Demo acquisition/expiry is a sibling's scope** (`AcquisitionAutomation`): FACEIT `demo_url` expiry etc. From this slice, the two facts that constrain acquisition: Valve replay hosts (`replay<N>.valve.net/730/*.dem.bz2`) are undocumented/not a stable API, and **official MM demos carry encrypted net-messages requiring the `.dem.info` key** (Sept-2026 change).
7. **Dead ends documented so they are not re-investigated:** `ekimroy/cs-demo-analyzer` (wrong owner), `demostf/cs-demo-analyzer` (nonexistent), `jsdemoparser` (no npm/GitHub artifact), `cs2-demoinfodb` (no repo), `democli` (no CS artifact), `demostf/rust-demoparser` (demostf's parser is TF2, moved to Codeberg), `markus-wa/demoinfocs-wasm` (last push 2023-06-01 → stale JS path), npm WASM `demoparser2` (frozen at 0.15.0, 2023-12-04).
8. **Quick wins for a local-first build (all evidenced):** use awpy `demo.load("rounds","kills",...)` for a single-pass multi-dataset load; `snapshots(every=64)` for downsampled per-tick series; `ticks(props)` for arbitrary prop extraction; `VisibilityChecker` reused across queries (BVH built once at construction); `awpy.data` for version-pinned map assets with `AWPY_DATA_DIR` for a repo-local cache (avoids `~/.awpy` surprises in CI); `NavMesh.find_path` + `plot.nav` for callout/route visualisation once a position→callout mapping is added (awpy still lacks an in-game callout lookup — open issue #390 "Provide function of Position -> Place name", 2025-03-30).
9. **Closed on request of slice `DemoDataFogOfWar` (their VERIFY item 2): the "just read the smoke voxels through awpy `ticks(props, players_only=False)`" shortcut does not exist.** `pbdems2 0.4.0` encodes `C_NetworkUtlVectorBase<T>` as a dynamic array whose **parent field key holds the element count** while elements occupy child field-path keys (`entity/field_decoder.rs:543-556,765-805` + `entity/entities.rs:314-330`), so a parent-key prop query yields a length (u64), not the byte grid; addressing ~32k child paths is impractical. Practical routes: port cs2parser's voxel decode, or fall back to awpy's r=144 smoke sphere. (Same field-path mechanism is why `m_bSpottedByMask.0000/.0001` appear as separate props in demoinfocs.)
