This section covers the *prior art* that most directly overlaps our target: local-first demo

## 7.1 pr1maly — closest existing prior art to the target system

- **Repo:** https://github.com/pr1malator/pr1maly · live demo: https://www.pr1maly.com/demo/match-breakdown.html?id=demo-01
- **What it does:** Standalone, locally-hosted CS2 analytics + trend tracker. Upload `.dem` → advanced player
  metrics → trends over time. All local, SQLite, no cloud services; AI features use *your own* API key.
- **Architecture (from README table):** 1) Parser = `demoparser2`; 2) Metrics = `pandas` (`src/processor.py`, `src/domain/`); 3) Storage = `sqlite3`; 4) Services (imports, Steam jobs, auto-sync, retention); 5) API = FastAPI + uvicorn, serves frontend; 6) Frontend = vanilla JS + Chart.js; 7) AI = `src/ai_service.py` + `src/services/ai_context.py` → OpenAI / Anthropic / Google Gemini / Mistral. Docker + docker-compose.
- **Exposed capability (verified from README):**
  - Metrics: HLTV 2.0 rating, ADR (capped at victim's remaining health so overkill doesn't inflate), KAST%, K/D, Impact, KPR/DPR, multi-kills (2K–5K), clutch 1vX detection, trade detection, full 10-player scoreboard with rank extraction.
  - Aim & movement: "aim score (0–100)", **counterstrafe detection**, **peek speed** (speed carried into the duel and whether counterstrafe held), stance breakdown, per-weapon movement penalties, reaction time, **crosshair placement quality**, time-to-kill efficiency.
  - Utility: grenades bought vs thrown vs wasted, flash efficiency (enemies flashed, blind duration, **team-flash penalty**), HE/molotov damage per throw, smoke zone coverage, utility rating.
  - 2D replay: canvas playback on radar images, 10 players, health bars, grenades with flight paths + countdowns, kill markers, animated kill feed. Interactive per-round minimap.
  - Behavioural: 5-axis chart (Aggression, Trading, Isolation, Survival, Sniper) per side, with win rate per dominant axis; **map-specific role detection** from coordinates (spider chart).
  - **AI coaching:** chat about any match, "round narratives with callout positions built automatically"; AI role assessment from positioning patterns.
  - Ops: sync folder (CS2 replays dir), optional **manual Fetch from Steam** via a separate Node companion in `fetcher/` (check for new matches, pull backlog), auto-sync with pause, storage management (**~280 MB per demo → ~1.3 MB analysed**, rolling retention window), `.dem.info` sidecar auto-detect, friends list, tags/notes, dark/light theme.
  - Map coverage: full callouts + role detection on Mirage, Dust2, Inferno, Nuke, Ancient, Anubis, Overpass; radar/minimap also Train, Vertigo, Office.
- **Status (2026-10-15):** 2 stars, 15 commits, `pushed_at` **2026-08-14** (last commit 2026-08-14), created 2026. Repo id 1206906723. Actively built by one author; no releases/tags visible.
- **License:** `LICENSE` = **"Source Available License – Non-Commercial"** (copyright pr1malator 2026): may use/copy/modify/distribute, but **shall not be sold, sublicensed, or commercially exploited for monetary gain** (explicitly incl. offering as a paid service or bundling with commercial products).
- **Linux compat:** Python 3.11+ (tested 3.11 & 3.14), Docker path available → Linux-hostable.
- **Reusability:** **Reference only.** Non-commercial license blocks code reuse in any monetised product. Valuable as a *feature checklist* and as evidence that the whole pipeline is achievable by one developer with `demoparser2` + SQLite.
- **AI: real or marketing?** Real but shallow — deterministic metrics computed in code, then **LLM used as a narrative layer** over pre-computed round facts (no model training, no learned decision evaluation). It is "stats → prose", not decision-quality inference.
- **Unsolved problems it leaves open:** no fog-of-war/enemy-visibility modelling; no counterfactual/alternative-decision evaluation; no per-habit aggregation with evidence; no evaluation of the coaching text itself; Windows-first (`setup.exe`-style UX), no API surface documented for programmatic use beyond its own FastAPI.

## 7.2 CS2DemoKit — the most relevant *architectural* prior art (fog-of-war + rules engine)

- **Repo:** https://github.com/CS2OpenDev/CS2DemoKit · **MIT**, .NET `net10.0`, **116 commits**, last commit **2026-09-25**.
- **What it is:** "A suite of libraries and tools for working with CS2 demo files", three NuGet-style packages, no UI:
  1. `CS2DemoKit.Parser` — frames + net messages, **270+ typed game events**, entity tracking with tick seeking, typed entity reads via the "CS2OpenDev entity contract".
  2. `CS2DemoKit.Analysis` — rule-driven analysis engine: **state-graph evaluator**, per-player stats, highlights, clip planning, **3D line-of-sight engine**. Depends on parser.
  3. `CS2DemoKit.Analysis.Rules` — rules DSL semantic core (lexer, parser, canonical AST, resolver, typed checker, canonical hashing), zero dependencies.
- **Line-of-sight / `enemy_spotted` (verbatim README):** *"A rule can trigger on `enemy_spotted`, the rising edge where one player first comes into view of another. Nothing on the wire says so; it is recomputed from baked map collision geometry."* `VisibilityEngine.Load(bake)` builds a **BVH over the mesh** ("tenths of a second on the large bakes"), immutable, shareable across runs. **Bakes are not shipped** — "the geometry is Valve-derived and large, and ships out of band"; located via `CS2DEMOKIT_COLLISION_DIR` (`<dir>/<map>.tris` or `<dir>/<map>/collision.tris`) or `assets/<map>/collision.tris`; a miss returns null so the capability degrades silently (a rule subscribing to `enemy_spotted` then *never fires* — a documented foot-gun).
  - **Category: Demonstrated** (documented, shipped in a real package, exact API shown) — **but only if you produce the collision bakes yourself.** Getting the bakes is exactly what `awpy-data` already does for awpy (`.mesh`, "decimated collision geometry for line-of-sight", `AWMH` format).
- **Player input (`svc_UserCmds`) — critical, recent finding:**
  - `svc_UserCmds` is **~90% of the net messages** in a demo (1.15 M messages on a 290 MB file) and "is read by almost nothing".
  - **Since ~July 2026 (build 10896) servers send almost every command as `delta_data`** — a patch against that player's previous command in Valve's own delta encoding, not protobuf. On current matchmaking demos **99.8–99.9% of commands are deltas**, so reading `data` alone sees "a fraction of a percent of the input".
  - `UserCmdReconstructor` rebuilds every command (view angles, buttons, movement, **subtick moves**); `SubTickExtractor.Extract(demo.Frames)` yields one `SubTickEvent` per move step. Baseline priming + self-checks (`CheckpointMismatches`, `ClientTickMismatches`, `UnknownFieldsSkipped`) reported in `reconstructor.Stats`.
  - **Why this matters to us:** per-tick *player input and intent* (what the mouse/keys actually did, including sub-tick press/release timing) is recoverable from demos — the raw material for decision-quality evaluation, not just outcomes.
- **Two tick clocks (load-bearing warning, verbatim):** *"CS2 demos carry two clocks and mixing them produces results that look plausible and are wrong."* Frame clock (index used by frames/rules/highlights, starts at 0) vs absolute server tick (`GameEvent.ServerTick`; converted via `ParsedDemo.ServerStartTick`). Any evidence-linked coaching system must pick one and convert explicitly.
- **Robustness design worth copying:** decode plans (`Everything`, `StructureOnly`, `GameEventsOnly`, `EntityReplay`); stream-and-drop so memory stays flat regardless of demo size; parser throws **only** when the input is not a CS2 demo, otherwise degrades (truncated/corrupt/hostile demos yield partial frames + warnings); `ParsedDemo.Health` = `Clean` | `Degraded` | `Damaged` (`Degraded` is normal for demos newer than the parser — do **not** gate a "damaged" banner on `Warnings.Count > 0`); enforced allocation limits (string-table 16 MiB, 4096 entries/table, instance-baseline 16 MiB, etc.).
- **Reuse verdict:** **Integrate-by-port / copy design, not code** (we are Python/local-first; this is .NET). Its rule-engine + visibility-event design is the single best template for our fog-of-war + mistake-rule layer, and its `enemy_spotted` rising-edge abstraction is exactly the primitive "you were seen / you could have been seen" detection needs.
- **Unsolved/open:** geometry bakes must be produced and hosted; `net10.0` + Go-1.27-style bleeding edge requirements; no eval of coaching output.

## 7.3 counterstrafe — open-source 2D replay + coach-review workflow (MIT, TypeScript)

- **Repo:** https://github.com/naeyn/counterstrafe · **MIT** (README badge; **no `LICENSE` file in repo root** — flagged as a compliance risk), TypeScript, **8 commits**, last commit **2026-01-22**.
- **Stack:** pnpm monorepo: `apps/*` + `packages/*`; React 18 + Vite + Tailwind + shadcn/ui + TanStack Query + React Router; backend **Fastify 5**; API on :3001, web on :5173; `pnpm typecheck|test|lint`.
- **Features (verified from README):** 2D replay with **player view cones**, health bars, 0.25×–4× playback, timeline scrubbing, round navigation, kill feed with headshots/wallbangs/multi-kills, grenade effects + death markers, all competitive maps; player stats (K/D/A, ADR, **HLTV 2.0 rating**, opening duels, clutches); economy analysis (per-round economy, buy patterns, equipment value graphs); **tactical analysis** — play pattern detection (A/B executes, mid splits, eco rushes), **player role classification (Entry, AWP, Support, Lurk, IGL)**, mid-round decision analysis, territory-control heatmaps; utility analysis (smoke coverage maps, flash effectiveness, grenade heatmaps, utility damage); **Coach Review System** — flag specific moments for review, categorised review queue, threaded discussions on flags, status tracking.
- **Assessment:** Conceptually closest to the *review-workflow* UX we want (flag → categorise → discuss), and it renders **view cones** (a visual cousin of fog-of-war, though cones here are geometric FOV, not occlusion-tested). Repository is a young, low-commit project (8 commits, 1 star, `AGENTS.md`/`CLAUDE.md` present → partly LLM-authored). Treat as design reference; verify code quality before reuse.
- **Unsolved/open:** no visibility/occlusion engine (view cones are drawn, not computed against geometry); no AI layer; no documented tests for the analysis math; dormant since Jan 2026.

## 7.4 DEMO-SLAP — commercial MCP connector + public API (clip rendering)

- **Site:** https://demo-slap.net/ · AI/MCP page: https://demo-slap.net/ai-api · API docs: https://api-doc.demo-slap.net/ (Swagger; spec `api-documentation.yaml`, **version 2.5.0**) · base `https://api.demo-slap.net`.
- **What it is:** Hosted CS2 demo analysis + **4K clip / fragmovie rendering** with an **OAuth-secured remote MCP connector** (Steam sign-in) usable from Claude, ChatGPT, Cursor, OpenCode — and a plain REST API (header `x-api-key`). MCP tools advertised: Analyze (submit demo URL → fetch results), Matches (list analysed matches), Match data (rounds, kills, highlights), Rendering (render clips, poll progress, get signed URLs), Fragmovies (stitch highlight videos).
- **Endpoints (verified in spec):** `POST /public-api/analyze/url` → analyze `jobId`; `GET /analyze/{jobId}/status`; `GET /analyze/{jobId}/data`; `GET /public-api/matches` (paginated); `POST /render/{jobId}` (by highlight ids); `POST /render-custom/{jobId}` (by `(tick, duration, povSteamId)`); `POST /render-fragmovie/{jobId}`; `GET /render/{jobId}/status` + `/data`; credit calculators.
- **Data exposed:** match (`map`, `matchTime`, teams, players w/ `steamId`, `isMe`, `source` enum incl. `faceit`, `match-token`, `upload`, `url`); highlights (`id`, `steamId`, `killCount`, `roundNumber`, `tags` e.g. `["3k","clutch"]`, `startTick`, `endTick`); per kill: `weapon`, `victim`, `ttd` (**time to first damage, ms**), `ttk` (**time to kill, ms**), `tick`, `killerSteamId`, `isHeadshot`, `noScope`, `throughSmoke`, `isWallBang`; top-level `tickRate` + `participants[]`.
- **Key limitation:** **no positional/tick-level data dumps, no aggregate stats.** It is a highlight/render service, not an analytics data source. Nothing about *fog of war*, positioning, or decision quality.
- **Pricing (from spec 2.3.0 note):** custom render ≈ **0.1 credits/s**, ×1.5 for `highResolution`, ×1.5 for `hideWatermark`, 1-credit floor; credits shared with the website; access/support via Discord.
- **Category:** Demonstrated, production (versioned API with breaking/additive changelog discipline).
- **Reuse verdict:** **Integrate (optional accessory).** Best used as an out-of-band *rendering* backend so we don't build HLAE/CS2-render automation ourselves; it cannot replace our analysis layer. Also a live competitor for "CS2 in your AI chat" — note it has *no* coaching/eval framing, only analysis + clips.

## 7.6 The Brokas/DemoQueryCS2 — scenario search over your own demos (recreation of the ggViz paper)

- **Repo:** https://github.com/TheBrokas/DemoQueryCS2 · live hosted demo: https://cs2analysis.com/demoquery/ (preloaded with **680+ pro matches from the 2026 season**) · v1.1.0 Windows installer.
- **What it does:** Draw hypothetical CT/T positions on a radar → find every moment in *your own* indexed demos matching them, with a similarity tolerance in game units, filtered by bomb state / buy type / alive counts → ranked, replayable moments. "A recreation of the **ggViz paper** (https://arxiv.org/abs/2107.06495) upgraded for CS2."
- **Method (verified from README — directly reusable as an algorithm):**
  1. **Nav clustering (build time):** each map's nav mesh (**~2,000–4,000 walkable areas**) is clustered into **~100–180 mid-sized nodes** by deterministic agglomerative graph merging; a **geodesic (walk-path) distance matrix** between all nodes is precomputed, plus a raster grid for O(1) point→node lookup. Built with **`awpy get maps` + `awpy get navs`** (dev only; shipped app is fully offline).
  2. **Ingestion:** `demoparser2` extracts **one state per second per live round** — positions, view angles, health, armor, money, inventory, flash state, sides, bomb state; per-round buy classification from carried equipment value incl. saved weapons (≤ $5,000 eco, ≤ $16,250 semi, else full); bomb-site plants; kills/assists; grenade detonations with travel paths; round win method. Stored in SQLite (`cs2sf.sqlite3`) as **compact tokens** (sorted per-side node ids) + **18-byte-per-player position blobs** (coords quantized to int16, "finer than a radar pixel"); node labels ("Mid", "BombsiteA") **learned from the demos' own `last_place_name` data**.
  3. **Search:** stage 1 vectorised **geodesic Chamfer** scan over all states of the map (walls respected — two points close through a wall are *far*); stage 2 **exact optimal-assignment re-rank**, `cost = max(node geodesic, Euclidean)`; consecutive matching seconds merge into "moments" ranked by average per-player offset in units.
  4. **Results:** snapshot cards + click-to-play playback (kill feed w/ timestamps, muzzle flashes, true-scale smokes/mollies + travel paths); scenario stats aggregated over the full matching population (CT/T win rate exact vs close, win methods, round-clock histogram, next-kill %, buy-type mix); "team cores" (named 3–5 player groups identified by Steam ID) with overlap reporting, applied without reparsing.
- **Why it matters:** this is a **worked, shipped implementation of cross-match similarity search grounded in nav-mesh geodesics** — the closest thing in the ecosystem to our "find my recurring situations" feature. The storage format (nav-node tokens + 18-byte position blobs) is a concrete, cheap design we can copy.
- **License/status:** root `LICENSE.txt` ("free for players, analysts and teams"; personal/team use) — **not OSI open source**; read the file before reuse. Last commit **2026-09-06**. Windows-only installer (unsigned).
- **Unsolved/open:** similarity is *positional* only — no utility/vision/decision semantics; no fog-of-war; no AI/coaching output; no evaluation of matched moments.

## 7.7 Twoos123/cs2-meta-engine — pro-demo mining + anti-strat (closest overlap on "coaching content")

- **Repo:** https://github.com/Twoos123/cs2-meta-engine · last commit **2026-10-03**, no root `LICENSE` file found (status unclear → treat as all-rights-reserved until confirmed).
- **What it does (verified from README):** ingests pro, FACEIT and own matchmaking demos; per-annotation extraction of "**every grenade throw**"; **clusters identical lineups and ranks them by impact**, including **stand/run/jump technique and left/right-click detection**, executes, and *"your throw vs the pro lineup"* feedback ("**12u left, 3° too high**"); full **2D match replay** with key moments (entries, clutches, multi-kills, eco wins) and shareable links to any round+second (`?round=14&t=38`); **anti-strat reports** (site hits, utility, AWP spots, CT setups, T defaults at 0:20) with shareable link + **PDF export**; player profiles (Rating 2.0, ADR, KAST, clutches 1v1–1v5, trade %); **practice lists** exported as a CS2 `.cfg` that cycles through lineups in-game with `]`/`[`; **live radar from CS2 Game State Integration incl. Nuke/Vertigo upper & lower levels**; imports (own MM demos auto-picked, **FACEIT demos via the official API**, HLTV demos via a one-click browser extension, archives `.rar/.zip/.dem.gz/.bz2/.zst`); runs locally or self-hosted on Kubernetes with Postgres + job worker + CI/CD + monitoring + IaC; mobile-responsive.
- **Why it matters:** (a) the **numerical line-up delta** ("12u left, 3° too high") is precisely the kind of *measurable, evidence-grounded micro-feedback* we want (vs. "improve your utility usage"); (b) it demonstrates the **grenade-throw geometry comparison** pipeline; (c) `last_place_name`/GSI are already used by peers for callout labelling and live state.
- **Unsolved/open:** "impact ranking" of lineups is heuristic, undefined in the README, and unevaluated; no fog-of-war; no decision-quality/counterfactual evaluation; no measured coaching efficacy; no documented license.

## 7.8 Cross-cutting notes for this section

1. **Every serious project converges on the same skeleton:** `demoparser2` (or awpy) → deterministic metrics in code → SQLite/Postgres → 2D radar replay → optional LLM narrative over pre-computed facts. **Nobody evaluates the LLM's coaching output**, and **nobody does fog-of-war / visibility-based decision evaluation** — the two clear differentiators left.
2. **Unexploited 2026 capability:** `svc_UserCmds` reconstruction (CS2DemoKit §7.2; demoparser2 `usercmd_*` fields) exposes real per-tick *input* (view angles, mouse deltas, button press/release, sub-tick move steps). Only hobby "aim score" implementations (pr1maly) touch it; nobody uses it for counterfactual decision evaluation.
3. **Visibility/occlusion:** only CS2DemoKit implements it, and only via out-of-band collision bakes. awpy ships the same idea first-class as `VisibilityChecker` + `map_control` (see §4/§1) — so this is not a research risk, it is an integration task.
4. **Licensing minefield:** pr1maly (Source-Available Non-Commercial), CS2-insight-agent (PolyForm NC), DemoQueryCS2 (free-for-use `LICENSE.txt`), DAK Studio (MIT/AGPL dual — AGPL is viral for network services), counterstrafe (MIT badge, **no LICENSE file**). Only **awpy, demoparser2, CS2DemoKit, counterstrafe(badge)** are permissive; **pr1maly and friends are read-only references.**
5. **Acquisition is a solved, repeatedly-duplicated pattern** (see §3 for the real verdict): FACEIT official API worker (VDAPI, cs2-meta-engine), Steam fetch companion (pr1maly `fetcher/`, DemoQueryCS2 hosted), Leetify fetch (CS2-RAG), HLTV browser extension (cs2-meta-engine).
